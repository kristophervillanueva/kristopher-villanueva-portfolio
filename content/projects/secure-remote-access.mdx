## The problem

Staff needed to work from home on **their own office PCs**, not on a generic remote desktop. That matters for the render workstations: applications like D5, Enscape, SketchUp, ArchiCAD and Revit depend on the GPU in the physical machine.

The requirements were unusually tight for a remote access project:

- **No budget.** No new per-seat licensing.
- **MFA required.** Password alone was not acceptable.
- **Protect the regional HQ link.** The site connects to the regional HQ over IPsec, with directory synchronisation involved. Anything that touched the wrong controller could put that link at risk.
- **Keep it usable.** People needed their files, their licenses and their desktop exactly as they left them.

## Constraints

- The environment runs an ageing Windows Server generation on the hypervisors. Adding an internet-facing VPN role to those hosts was not defensible.
- The FortiGate already terminates the HQ tunnel and its own management services. Only one inbound path could be opened, and it had to be narrow.
- The directory had controllers in more than one region. The safest target was a single, local controller addressed explicitly.
- Unverified assumptions were common at the start. The project needed a habit of testing each link in the chain separately.

## Architecture

<Diagram />

The path has two distinct halves, and separating them made the troubleshooting tractable.

**Authentication:** the client presents a certificate, an Active Directory password and a TOTP code. The OpenVPN server hands the credentials to FreeRADIUS, which asks privacyIDEA to validate the one-time code, and privacyIDEA checks the password against Active Directory over LDAPS. Only when all of that succeeds does the tunnel carry traffic.

**Session:** the tunnel routes only the office VLANs. From there a user reaches their own workstation with RDP, or UltraVNC for render machines that need a console session and dual monitors.

Two details carried most of the risk:

1. **The explicit hostname.** Pointing LDAPS at the bare domain name would have resolved to the regional HQ controllers. The configuration named one local controller directly, so directory changes stayed local.
2. **The private CA.** That controller had no certificate of its own. I created a private CA with OpenSSL, issued a certificate for that server, and imported it — a two-hour task that unblocked the entire identity chain.

## The identity chain

The three factors are not decorative. Each covers a different failure:

- The **certificate** is bound to the device. A password typed somewhere else is useless without it.
- The **directory password** ties access to a real, disableable account.
- The **TOTP code** covers the case where the password is known and the device is not.

The password and the six-digit code are entered together, which keeps the client experience to one prompt. Behind it, FreeRADIUS and privacyIDEA do the separation.

## Hardest faults

These were the failures that took the longest, and each one changed how I troubleshoot.

### RDP blocked although packets arrived

Everything looked correct and traffic reached the gateway, but nothing came back. The cause was an OPNsense tunnel interface that had been assigned but never enabled — a single unchecked box. The lesson: verify the interface state, not just the firewall rule that references it.

### The same symptom on a workstation

A workstation showed an identical "connection refused" pattern. The firewall exception was correct. Windows Firewall's **"Block all incoming connections"** setting overrides every individual exception, including the one just created.

### An orphaned instance in the VPN service

A DCO error kept the service from starting cleanly. The cause was an orphaned instance identifier. Disabling DCO hid the symptom; clearing the stale instance fixed it.

### A firewall policy that did not match its interface

Traffic matched the wrong policy because the destination interface referenced raw ports instead of the VLAN interfaces. Fortinet TAC and `diagnose debug flow` together showed the real match path. Reading the flow trace was faster than reasoning about intent.

### LDAPS resetting the connection

A "connection reset" during the directory binding was most likely caused by StartTLS being enabled while using an `ldaps://` URI — asking for TLS twice. Several settings changed at once during that window, so this is a likely cause rather than an isolated proof.

### A rule named "deny" that accepted

One firewall rule was named as a deny for RDP and VNC, and its action was accept. Nothing in the name, the description, or the surrounding documentation said so. I found it by opening the live form and reading the action field. The lesson is now a habit: **read the action, not the label.**
