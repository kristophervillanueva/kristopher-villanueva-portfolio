## The problem

Virtualisation consolidates several workloads onto one physical host. That is efficient, but it also concentrates risk: a host, storage, or software failure can take out multiple services at once. In the same way, backup data that lives on the same disks as the workloads is not really a backup — it shares the failure.

The environment had working virtual machines and a backup product in place. What it lacked was separation. Backup storage, production storage and the recovery procedure were not clearly distinct, and recovery had not been demonstrated.

## Constraints

- **No new licensing budget.** The solution had to work with Veeam Community Edition and tooling already owned.
- **The virtualisation layer could not be rebuilt.** The backup design had to fit the host as it existed.
- **Backup data could not sit on production disks.** A host failure must not destroy the recovery points with it.
- **The procedure had to be usable by one person.** A recovery plan that needs a specialist vendor on the phone is not a recovery plan.
- **Anything unverified had to be labelled.** A green job status is not evidence that a restore works.

## Architecture

<Diagram />

Three things are deliberately separate. The **production tier** is the Hyper-V hosts and their guests. The **backup tier** is Veeam plus the primary TrueNAS system. The **second copy** is the secondary TrueNAS system on separate hardware.

Veeam writes virtual-machine recovery points to the primary system on a four-hour interval, retaining fourteen restore points in the documented configuration. Windows Server Backup captures a system image of the physical host, so the hypervisor itself has a recovery path that does not depend on the hypervisor running. Selected datasets then replicate to the secondary system.

An important limit, and one worth stating plainly: **replication is not a hot standby for the Veeam repository.** Using the replicated data means reconfiguring the repository and validating the backup chain. Treating the secondary system as a drop-in replacement would be an assumption, not a design.

## What the tests actually proved

<Callout title="File-level restore — tested">
A file was recovered from an available restore point and its contents and permissions were checked. The path works. The elapsed time and the age of the recovered point were not recorded at the time, so no RTO or RPO figure is claimed from it.
</Callout>

<Callout title="Virtual-machine restore — tested">
A virtual machine was restored from a successful recovery point and started. Operating system, networking and the services checked at the time came up. Any manual steps taken during the restore were noted as part of the procedure.
</Callout>

Two restores working is a meaningful result: it proves the backup chain is usable and the procedure is followable. It is not the same as a measured recovery capability. Without timings, a business-approved target and a repeatable test record, an RTO number would be an estimate dressed up as evidence.
